# D2 reference

## Provenance and compatibility

This is an original, compact synthesis of first-party documentation, with locally authored examples; it is not a vendored third-party skill or a complete documentation mirror. Sources below are pinned to [`d2lang/d2-docs` revision `9231f19fbb929cca9c36734a8be65b44dfd4cfee`](https://github.com/d2lang/d2-docs/tree/9231f19fbb929cca9c36734a8be65b44dfd4cfee). That documentation revision is newer than our tested CLI; the bundled examples and workflow commands were separately checked with **D2 0.7.1**. The installed CLI and actual rendering take precedence over assumptions about newer features.

To update: inspect the relevant official pages at a new commit, update these notes and the revision together, then repeat the example checks below with the configured D2 version and visually inspect the outputs. Layout defaults and the repair workflow are local recommendations, not upstream requirements.

## IDs, labels, and connections

An object is `id: Display label`; its default shape is a rectangle. Set `shape` in its map, for example `database: Database {shape: cylinder}`. Use short IDs (`api`, `database`) for references rather than labels. Keys are case-insensitive. Quoting keys permits reserved words as literal names, useful for a SQL column such as `"label"`.

Connections use `->`, `<-`, `<->`, or `--`; append `: relationship` for a label. An edge referencing an undeclared ID creates a node, so a spelling mistake can render successfully. Repeating an edge creates another edge; to modify the first existing one use its zero-based index, such as `(api -> database)[0].style.stroke-dash: 3`. Double-headed arrows communicate a relationship in both directions, not message ordering; use separate labeled edges when the directions mean different things.

Sources: [shapes][shapes], [connections][connections], [SQL tables][tables].

## Containers and scope

A nested map creates a container: `system: Application {api: API; worker: Worker}`. Reference its children from the root as `system.api` and `system.worker`. Within a container, `_` moves to the parent scope. A new unqualified ID inside a container belongs to that container, not to the root. Prefer root-level, fully qualified cross-container edges when that makes ownership clearer.

Use the [architecture starter](../examples/architecture.d2) for a working nested example. Sources: [containers][containers] and its [parent-scope example][parent-scope].

## Layout and repeatable configuration

The starters put `layout-engine` and `theme-id` under `vars: {d2-config: {...}}`. This preserves rendering intent in the editable source. Flags and environment variables override those values; check `D2_LAYOUT` and related variables if a render behaves unexpectedly. Use `d2 themes` to list installed theme IDs and `d2 layout elk` or `d2 layout dagre` for engine-specific options.

- **Dagre** is a good first pass for simple directed flows.
- **ELK** is a good first pass for nested architecture and ER diagrams. The official SQL docs specify ELK or TALA for edges targeting exact table rows.
- Set `direction: right` for horizontal flow or `direction: down` for vertical flow. `left` and `up` are also valid.
- With Dagre/ELK, treat direction as global. Per-container direction, object-relative `near`, and fixed `top`/`left` positioning are not portable substitutes for automatic layout. Consult the engine docs before relying on constraints.
- Dagre does not support ancestor-to-descendant connections. Model the actual endpoint, or use an engine that supports the needed relationship; do not silently remove a real relationship to satisfy layout.

Sources: [layouts][layouts], [configuration variables][vars], [SQL tables][tables]. Local engine preferences are starting points; visual results decide.

## Reusable styling

Define a named entry under `classes` and apply `class: name` to nodes or edges. Explicit attributes on an object override its class. Put visual attributes inside `style` (or use dotted paths): `fill`, `stroke`, `font-color`, `font-size`, `stroke-width`, `stroke-dash`, and `border-radius`. Quote hex colors (`"#e8f0fe"`) because `#` introduces a comment. Use numeric `stroke-dash`, not CSS `dashed`.

Reuse styles by semantic role, as in the architecture starter, rather than styling every object differently. For SQL tables, `fill` colors the header and `stroke` also affects the body; start with the theme instead of assuming ordinary rectangle styling. Sources: [classes][classes], [styles][styles].

## Flowcharts

Use ordinary nodes and directed edges; a decision can use `shape: diamond`. Label each outgoing decision branch (for example, `yes` and `no`) and make terminal outcomes explicit. Source order is not a positioning guarantee in an ordinary graph. Use the [flowchart starter](../examples/flowchart.d2); layout direction expresses the preferred flow, not exact coordinates.

Sources: [shapes][shapes], [connections][connections], [layouts][layouts], and the ordering distinction in [sequence diagrams][sequences].

## Sequence diagrams

Set `shape: sequence_diagram`. Declare participants in desired left-to-right order before messages; write messages in chronological order. Unlike an ordinary graph, declaration order matters here. A nested unconnected container containing messages is a group; participants referenced from groups must already exist at the sequence's top level. Sequence groups share participant scope rather than creating a fresh copy of each participant.

Connect a nested object on an actor to represent an activation span. An unconnected nested object on an actor is a note. Use these when they clarify the interaction, not just to decorate it. The [sequence starter](../examples/sequence.d2) demonstrates participants, a group, and dashed return messages without extra activation detail.

Source: [sequence diagrams][sequences] and its [group example][sequence-group].

## ER diagrams

Set `shape: sql_table`; child keys are column names, and their values are displayed types. Column maps can set `constraint: primary_key`, `foreign_key`, or `unique`; arrays permit multiple constraints. Connect a foreign-key column to the referenced column with qualified IDs, for example `orders.customer_id -> customers.id`.

A foreign-key constraint alone does not create the edge or prove cardinality. Read the schema's nullability and uniqueness constraints before asserting optionality or one-to-one/one-to-many semantics. For crow's-foot notation, use an edge with both endpoints (`<->`) and set `source-arrowhead.shape` / `target-arrowhead.shape` to the appropriate `cf-one`, `cf-one-required`, `cf-many`, or `cf-many-required`; verify their rendered meaning. The [ER starter](../examples/erd.d2) instead uses a plain foreign-key arrow and makes no cardinality claim.

Sources: [SQL tables][tables], its [foreign-key example][table-fk], and [arrowheads][connections].

## Repeat the bundled checks

Run in this skill directory, with D2 on `PATH`. Formatting checks leave the starters unchanged; outputs go to a fresh temporary directory. These checks cover the four starters, not every optional syntax described above.

```sh
set -eu
out=$(mktemp -d)
d2 --version
d2 fmt --check examples/*.d2
for source in examples/*.d2; do
  d2 validate "$source"
  svg="$out/$(basename "$source" .d2).svg"
  d2 "$source" "$svg"
  test -s "$svg"
done
printf 'Inspect rendered SVGs in %s\n' "$out"
```

Open each SVG and apply the visual checklist in [SKILL.md](../SKILL.md). To compare engines, render to separate temporary filenames with `--layout=dagre` and `--layout=elk`, rather than overwriting an accepted output. CLI syntax above was checked against `d2 --help` in version 0.7.1.
